# Proton Mail Bridge on hailmary

## Connection details

Proton Mail Bridge runs on `hailmary` and only listens locally. Traefik exposes
trusted implicit-TLS mail endpoints for clients such as Apple Mail. Two
user-level `socat` forwarding services provide private Docker-network backends
for Traefik:

| Protocol | Client endpoint | Traefik backend | Bridge endpoint |
| --- | --- | --- | --- |
| IMAP over TLS | `protonmail.home.elikesbikes.com:993` | `172.18.0.1:21143` | `127.0.0.1:1143` |
| SMTP over TLS | `protonmail.home.elikesbikes.com:465` | `172.18.0.1:21025` | `127.0.0.1:1025` |

The `127.0.0.1` address reported by the Bridge `info` command is normal. It is
the internal endpoint, not the address to configure on another computer. The
Docker-network endpoints are private implementation details and must not be
used by clients.

## iPhone / Apple Mail settings

Configure the account manually with these settings:

| Setting | Incoming IMAP | Outgoing SMTP |
| --- | --- | --- |
| Host name | `protonmail.home.elikesbikes.com` | `protonmail.home.elikesbikes.com` |
| Port | `993` | `465` |
| Use SSL | On | On |
| Authentication | Password | Password |
| Username/password | Generated by Bridge | Generated by Bridge |

Traefik terminates TLS on ports 993 and 465 with its Let's Encrypt certificate,
then privately forwards plaintext IMAP/SMTP to Bridge. This deliberately uses
implicit TLS rather than Bridge's original STARTTLS endpoints, so the iPhone
validates Traefik's certificate instead of Bridge's generated certificate.

The hostname resolves to Hailmary's LAN address (`192.168.5.25`) through the
home DNS resolver. An iPhone must be on the home Wi-Fi with DNS set to
**Automatic**, or connected to Tailscale; public DNS resolves the name to
Hailmary's Tailscale address (`100.118.139.6`), which is unreachable without
Tailscale.

Use the generated Bridge username and password, never the normal Proton account
password. Do not disable TLS certificate validation globally.

## Retrieve the generated client credentials

On hailmary, briefly stop the background CLI, run `info`, then start it again:

```bash
systemctl --user stop proton-bridge-cli.service
protonmail-bridge -c
```

At the `>>>` prompt, enter:

```text
info
```

Record the Bridge username and password privately. Then enter `exit` and run:

```bash
systemctl --user start proton-bridge-cli.service \
  proton-bridge-imap-lan.service proton-bridge-smtp-lan.service
```

Stopping the CLI also stops its dependent forwarding services, so start all
three services after leaving the interactive shell.

## Services

All services run as the `ecloaiza` user, are enabled at boot, and are located in
`~/.config/systemd/user/`:

- `proton-bridge-cli.service` runs `protonmail-bridge -c` headlessly.
- `proton-bridge-imap-lan.service` forwards private `172.18.0.1:21143` to
  Bridge's localhost IMAP endpoint.
- `proton-bridge-smtp-lan.service` forwards private `172.18.0.1:21025` to
  Bridge's localhost SMTP endpoint.

Check them with:

```bash
systemctl --user status proton-bridge-cli.service \
  proton-bridge-imap-lan.service proton-bridge-smtp-lan.service
```

Restart all of them with:

```bash
systemctl --user restart proton-bridge-cli.service \
  proton-bridge-imap-lan.service proton-bridge-smtp-lan.service
```

## Where credentials and mail data are stored

Bridge stores its encrypted vault and configuration under:

```text
~/.config/protonmail/bridge-v3/
```

`vault.enc` contains Bridge's encrypted local vault, including the account
configuration and the generated client credentials. Local cached mail data and
logs are stored below `~/.local/share/protonmail/bridge-v3/` and
`~/.cache/protonmail/bridge-v3/`.

The key that unlocks the Bridge vault is stored in the `pass` password store as
an encrypted entry below:

```text
~/.password-store/docker-credential-helpers/.../bridge-vault-key.gpg
```

`pass` uses a dedicated GPG key stored in `~/.gnupg/`. This key was created for
the headless service with no interactive passphrase so Bridge can start after a
reboot. Therefore, anyone who can read the `ecloaiza` account's home directory
or log in as that user can potentially access the local Bridge data and client
credentials. Keep the host account and backups protected.

## Known issues

### ALPN `imap` rejected by Traefik (iPhone IMAP)

iOS sends an ALPN (Application-Layer Protocol Negotiation) TLS extension with
`"imap"` when connecting to port 993. Traefik's default TLS configuration does
not recognize `"imap"` as a valid application protocol and silently drops the
connection. SMTP is unaffected because iOS does not send ALPN for SMTP.

The symptom is that outgoing mail works but the inbox never loads — no error is
shown on the phone. The Traefik log reports:

```
tls: client requested unsupported application protocols (["imap"])
```

**Fix:** A custom TLS options block in the Proton Bridge dynamic config
(`config/dynamic-hosts/hailmary/proton-bridge.yaml`) declares `imap` as an
accepted ALPN protocol. Traefik must be **restarted** after changing TLS
options — a hot-reload is not enough.

### Apple Mail "Notes" folder (iPhone)

Apple Mail on iPhone automatically tries to create a "Notes" IMAP folder on the
server. Proton Bridge rejects this with `invalid mailbox name ["Notes"]:
operation not allowed`, which blocks the entire IMAP sync. Outgoing mail (SMTP)
is unaffected.

**Fix:** On the iPhone, go to **Settings → Mail → Accounts → [Proton account]**
and toggle **Notes OFF**. Only Mail needs to be enabled. If the toggle does not
take effect, delete the account entirely and re-add it with Notes off from the
start — iOS caches the CREATE command even after the toggle is changed.

### "invalid return path" on send

If SMTP returns `Send mail failed. error="invalid return path"`, the From
address configured in Apple Mail does not match the Bridge account address
(`ecloaiza@proton.me`). Verify the outgoing mail address in the account settings
matches exactly.

## Network security

- Traefik owns the public-facing ports 993 and 465. Bridge and its `socat`
  backends are not directly reachable from the LAN.
- This does **not** add firewall source filtering. Any machine with a route to
  `192.168.5.25` can attempt to connect. Do not create router port-forwards for
  ports `993` or `465`.
- Access is protected by the generated Bridge password and TLS. Treat
  that password like a mail password and do not store it in plaintext configs.
- For stronger enforcement, add a host firewall rule permitting TCP ports 993
  and 465 only from `192.168.5.0/24`; do this carefully because hailmary hosts
  other services.
- Bridge is designed primarily as a local proxy. Keep it and the host updated,
  and only grant LAN access to devices you trust.
